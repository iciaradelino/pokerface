# Decision records

Each record states the context, the decision, the alternatives we rejected and the consequences.

## Storage and data model of the players service

**Status:** accepted, 11 November 2026. **Owner:** Laura. Tables and columns are in [data-model.md](data-model.md).

### Context

The players service stores profiles and chip balances, records the result of each hand sent by the game service, and serves the leaderboard. The game service retries when a call times out, so saving a result must be safe to repeat, and results can arrive late or in a different order than the hands were played. The course requires one database per service, SQL Server locally and a serverless Azure SQL database in the cloud. We only use the plain `mssql` driver and our own migration runner, with no ORM.

### Decision

- **Two tables in the `players` database:** `players` (name, avatar, chips, gesture settings) and `hand_results` (one row per player per finished hand). Only the players service reads them. The game service uses HTTP.
- **Identity:** a UUID generated by the database. There are no passwords. The browser keeps the id in `localStorage`, as in the plan.
- **Chips are derived from the results.** The balance is the starting stack (1000) plus the sum of every saved `delta`, limited to 0 up to the maximum `INT`. `players.chips` stores this value so that reading it and the leaderboard are cheap, and it is recomputed from `hand_results` inside the same transaction that inserts a result.
- **Safe retries:** the primary key of `hand_results` is (`hand_id`, `player_id`). A result whose key already exists changes nothing and still answers 200. The player's row is locked during the save, so two retries arriving together run one after the other.
- **Index on `hand_results(player_id)` including `delta`** (migration `003`), so the sum only reads the rows of one player.
- **Leaderboard:** a query on `players.chips` (top 10, ties broken by name), with no table of its own. It lives in the players service so it keeps working when the game service is down.
- **Small choices:** the avatar is a hex colour, gesture settings are JSON text checked with `ISJSON`, and `chips >= 0` is enforced by a `CHECK` constraint.
- **Raw SQL** with parameters, in one repository module, so the routes can be tested with an in-memory fake.

### Alternatives considered

- **Adjust the balance with each result** (`chips = max(0, chips + delta)`). This was our first version. It depends on arrival order: if a loss of 1500 arrives before an earlier win of 1000, the balance is clamped to 0 and the win then gives 1000 instead of 500. A reviewer found it and we replaced it.
- **No `chips` column, computed on every read.** Always correct, but the leaderboard would sum every result of every player on each request.
- **Allow negative balances.** Simpler arithmetic, but a player with negative chips makes no sense at a poker table.
- **A shared database with the game service.** Breaks the one-database-per-service rule and couples the services.
- **An ORM.** More packages and more to learn for four small queries. We also keep the migrations as plain numbered SQL files.
- **Storing avatars as images.** Needs file storage, which is out of scope. A colour plus the player's initials is enough for the UI.

### Consequences

- Retries and late results are safe, and the leaderboard works when the game service is down.
- The same starting stack of 1000 appears in the migration default and in the repository code (`STARTING_CHIPS`). They must be changed together.
- Each save sums all results of that player. The index makes this a seek, which is fine at our scale. If a player had very many hands we could keep a running total instead.
- Deleting a player deletes their results (`ON DELETE CASCADE`), so their history is lost.
- There is no real authentication: anyone who knows a player's id can edit or delete that profile. This is accepted for games between friends, as in the plan.
- Without the index in `003`, six players saving results at the same time made 145 of 150 saves fail with a 503 because of SQL Server deadlocks. With it all 150 succeed. We checked this with a manual load script. The unit tests use an in-memory repository, so they do not run the SQL and do not catch locking problems.


## Poker engine (the non-CRUD feature)

**Status:** accepted, 12 November 2026. **Owner:** Olivia. Code and usage are in [services/game/src/engine/README.md](../services/game/src/engine/README.md).

### Context

The core of Pokerface is No-Limit Texas Hold'em for 2 to 6 players. The rules are the most complex logic in the system: betting rounds, minimum raises, all-ins, side and split pots, and ranking hands. A bug here costs players chips. The server knows every player's hole cards, but each player may only see their own. The game service needs at least 70% test coverage on its core logic, and the message formats between the game service and the browser are fixed in `plan.md` §6.

### Decision

- **A pure engine** in `services/game/src/engine/`: plain functions with no Express, database or WebSocket code. Each function takes the table state and returns a new one without changing the input, so a rejected action never leaves a table half-updated.
- **The server decides.** The browser only sends what the player wants to do (`{ action: "raise", amount: 60 }`). The engine checks it against the legal actions and rejects anything else with a stable error code, such as `NOT_YOUR_TURN` or `INVALID_AMOUNT`.
- **Our own hand evaluator.** It scores all 21 five-card combinations of a player's seven cards. It is our non-CRUD feature, so we wrote it ourselves to understand and explain it.
- **Secure shuffling** with Node's `crypto.randomInt` (Fisher-Yates), so the next cards cannot be predicted.
- **`amount` means "raise to"**: the player's total bet on this street after the raise, not the chips added. The raise slider and the gesture send the same number the player sees.
- **An adapter for the §6 formats** (`messages.js`, the Adapter pattern). The engine was written before §6 was agreed, so its names and shapes differed: `phase` instead of `stage`, `allIn` instead of `allin`, and one view per player instead of a public `state` plus a `private` message. A small adapter translates in both directions: engine state into the §6 messages, incoming actions into engine actions, finished hands into `POST /players/:id/results` bodies, and engine errors into HTTP status codes (400 for a bad request, 409 for a rule violation).

### Alternatives considered

- **Rules inside the Express routes.** Less code at first, but the rules could only be tested through HTTP, and two routes changing the same table could break each other.
- **A hand-evaluator library** (e.g. pokersolver). Faster to start, but it would hide the logic we must explain, to save about 100 lines of well-tested code.
- **Rewriting the engine to match §6** instead of adding an adapter. One file less, but it would have changed working, tested code only to rename fields.
- **`Math.random` for shuffling.** Simpler, but its output can be predicted.

### Consequences

- The rules are tested without a server or database: unit tests for every rule, fixed decks that deal known cards, and random play of hundreds of hands that checks that chips are never created or lost and that no message ever contains another player's hole cards. Engine coverage is about 96%, which keeps the game service above 70%.
- Only `messages.js` knows the §6 formats. If they change, one file changes and the engine does not.
- The table is a plain object in memory, so a hand in progress is lost if the container scales to zero (see the architecture decision).
- Simplifications for the MVP: the dealer button moves to the next player with chips, and all remaining hands are shown at showdown (no hiding a losing hand).


## Game service architecture: live tables, HTTP and WebSocket

**Status:** accepted, 18 November 2026. **Owner:** Lara. Tables and columns are in [data-model.md](data-model.md); results delivery is in the next record.

### Context

The game service runs private tables of 2 to 6 players with Olivia's engine. Every action has to reach the other players at once, each player may only see their own hole cards, and a turn lasts at most two minutes. The plan deploys each service as an Azure Container App with min 0 / max 1 replica, so the container can scale to zero when nobody plays, and a serverless Azure SQL database that may be paused. The service must keep working when the players service is down.

### Decision

- **The hand in progress lives in memory.** The engine state of each table (deck, hole cards, bets, whose turn it is) is a plain object in the game service. The database keeps what must survive a restart: the table and its settings, the seats with their stacks, and every finished hand with its results.
- **One replica.** One process owns every table, so there is no shared state between servers. A table is loaded into memory the first time it is used, from its saved seats, stacks and last hand number.
- **One queue per table.** Every change to a table (join, leave, action, timer, saving a hand) runs in order through its own promise queue, so two requests never interleave on the same table. Different tables do not wait for each other.
- **A finished hand is saved in one transaction** (the hand, each player's result and the new stacks). If the database fails, the table retries every 3 seconds with the same hand id and starts no new hand until it is saved.
- **HTTP for actions, WebSocket for state.** The browser sends actions with `POST /tables/:id/actions` and gets a status code: 400 for a malformed request, 409 for a rule violation. The server pushes the public `state` to everyone at the table and a `private` message with each player's own cards over `ws(s)://…/tables/:id/ws?playerId=`. The same socket relays the WebRTC signals for the webcams, with the sender set by the server.
- **The `ws` package** on the same HTTP server, with an origin check before the upgrade, close codes the UI can act on (4400 bad request, 4403 not seated, 4404 table not found, 1011 database down), a 30-second heartbeat and a 64 KB message limit.
- **The server runs the table.** A hand starts on its own 5 seconds after two players with chips are seated, unless the creator has not pressed Start game yet or has paused the table. A player who does not act in 2 minutes checks if possible, otherwise folds.

### Alternatives considered

- **Save the hand state after every action.** A restart would not lose the hand, but every action would wait for a database write, a paused serverless database would freeze the game, and the hole cards would have to be stored.
- **Shared state in Redis to allow several replicas.** Another service to deploy, secure and pay for, and the per-table queue would become a distributed lock. Our load (a few tables of friends) does not need it.
- **Actions over the WebSocket too.** One channel, but HTTP gives status codes, request validation, request logs and easy tests with supertest, and the UI already used HTTP for everything else.
- **Polling instead of WebSocket.** The waiting room polled every 3 seconds before the socket existed. It is simple, but a 3-second delay on every action is too slow for a game.
- **Server-Sent Events.** Push only from the server, so the WebRTC signals from the browser would need another channel.
- **Socket.IO.** Rooms and reconnection built in, but a heavier library with its own protocol on both sides. The browser's native WebSocket plus `ws` is enough.

### Consequences

- A restart or scale-to-zero loses only the hand in progress. Tables, seats with their stacks and finished hands are kept, and the table continues from the next hand number.
- The game service cannot scale out: with two replicas, two players at the same table could reach different processes. Max 1 replica is a requirement of this design, not only a cost choice.
- Rules and timing are tested without a database: the routes and live tables run against an in-memory fake repository with fake timers, and the socket tests use real WebSocket connections.
- On Azure the UI must use `wss://`, and `UI_ORIGIN` must match the UI's address or the origin check refuses the socket.
- When the database is down, a finished hand waits in memory until it can be saved; if the container stops during that time, that hand is lost too.


## Partial failure: delivering hand results to the players service

**Status:** accepted, 19 November 2026. **Owner:** Lara. The `hand_players` table and its rules are in [data-model.md](data-model.md).

### Context

When a hand ends, the game service knows how many chips each player won or lost, but the chip balances belong to the players service and its own database. There is no transaction across the two databases, and the players service can be down, slow or restarting at any moment. A player's chips must never be lost or counted twice, and an outage of the players service must not stop the tables. The players service ignores a `handId` it has already saved for a player, and it refuses a `delta` above 1,000,000,000.

### Decision

- **Results are stored before they are sent.** Each finished hand writes one `hand_players` row per player, with `sent_at` empty, in the same transaction as the hand and the new stacks. The game service then sends the rows with `POST /players/:id/results { handId, delta }`. This is the transactional outbox pattern: a saved hand always has its results waiting to be delivered.
- **Sending is retried until it succeeds.** A sender runs after every saved hand, once a minute and at startup. It sends the oldest results first, in batches of 50, with a 2-second timeout per call, and only one round runs at a time.
- **Each answer has a fixed meaning:**
  - 200: delivered, `sent_at` is set.
  - 404: the player deleted their profile, so the row is marked as sent and never retried.
  - Any other 4xx: the players service refused the result for good. The row gets `rejected_at`, is logged as `result_rejected` and is skipped, so it cannot block the results behind it.
  - Timeout, network error or 5xx: the players service is unavailable. The row stays pending and the round stops, so a service that is down is not flooded. The next round tries again.
- **A retry never counts twice.** The `handId` is the `hands.id` UUID, and the players service ignores a `handId` it already has for that player.
- **The tables keep playing.** Creating or joining a table checks the player with `GET /players/:id` and answers `503 PLAYERS_UNAVAILABLE` if that fails, but the player's name is copied into the seat, so the players at a table can go on playing. Their results queue up and arrive when the players service is back.
- **A table with undelivered results cannot be deleted.** Deleting a table also deletes its hands and their `hand_players` rows, so `DELETE /tables/:id` answers `409 RESULTS_PENDING` until every result is sent or rejected.
- **One chip limit per table.** A table never holds more than 1,000,000,000 chips in total (`starting_stack × max_seats` on creation, and the sum of stacks when someone joins), which is the players service's limit on `delta`. Nobody can win more than everyone else at the table has, so no valid hand can produce a result the players service refuses.

### Alternatives considered

- **Call the players service when the hand ends and fail if it is down.** Simpler, but an outage of the players service would stop every table, or the hand would have to be rolled back.
- **Send once and forget.** Results sent during an outage would be lost, and so would the chips.
- **A message queue such as Azure Service Bus.** The standard tool for this, but another resource to deploy, secure and pay for, while the outbox only needs one table in the database we already have.
- **The players service pulls results from the game service.** It would have to read the game service's data and know when to ask, coupling the services in the other direction.
- **Retry every failure, including 4xx.** This was our first version. A reviewer showed that one refused result blocked every result behind it, so a refusal is now marked as rejected.
- **Keep the results when a table is deleted** (no cascade, or copying them to another table). It avoids the 409, but needs more schema and a second place to send results from. Results are usually delivered within seconds, so blocking the delete for a short time is simpler.

### Consequences

- Delivery is at least once and eventually consistent: during an outage a profile shows its old chips, and it catches up within a minute of the players service coming back. Safe retries make "at least once" count as exactly once.
- A rejected result is kept but nobody is notified automatically; someone has to look for the `result_rejected` warning in the logs. With the chip limit, it should only happen if the two services' rules drift apart.
- The limit of 1,000,000,000 is written in both services. `resultLimits.test.js` imports the players service's own validation, so the tests fail if one service changes it and the other does not.
- The creator may have to wait up to a minute to delete a table after an outage.
- The tests cover each answer of the players service with a fake client, and one test sends results to an HTTP server that uses the players service's real validation.

## Azure deployment and pipeline

### Context

We need to deploy the same commit that passed CI and be able to repeat the deployment inside our assigned Azure resource group.

### Decision

We use Bicep and GitHub Actions. After CI passes on `main`, the deploy job publishes both backend images to GHCR with the commit SHA as the tag. It signs in to Azure using the group's managed identity and OIDC. Bicep sets up the shared hosting resources first, then the pipeline creates a separate user in each database and deploys both Container Apps. The services run their migrations at startup. The workflow builds and uploads the UI with the deployed backend URLs, then checks both health endpoints and the UI.

### Alternatives considered

- Manual portal setup would get the first version online, but it would be harder to reproduce and review than Bicep.
- A shared SQL admin login would be simpler to wire up, but each service would have access to both databases.

### Consequences

The two images must be public so Container Apps can pull them without a registry password. SQL credentials live in GitHub and Azure secrets. The first deployment needs the professor's identity setup and an explicit repository opt-in. Deployments fail if either backend does not report the expected version or the live UI cannot be reached before the smoke test times out.

## Monitoring and game action SLO

### Context

We need to see real request load, server errors and response times on Azure, and measure whether poker actions respond quickly enough during play.

### Decision

We query the JSON request logs that both Container Apps already write to Log Analytics. A shared Azure Workbook shows the last 24 hours by service. A saved query measures whether 99% of eligible game actions return 2xx in under 300 ms over seven days. A 5xx counts as a failure; a 4xx does not count toward the target. Health checks, preflights and WebSocket upgrades are excluded from the HTTP dashboard.

### Alternatives considered

- Platform metrics give us broad traffic and latency numbers, but don't isolate the poker action route.
- A separate monitoring service would add another system to deploy when the existing workspace already receives these logs.

### Consequences

Bicep deploys the shared workbook and saved query with the workspace. The SLO measures server response time for requests that reach the app; it doesn't measure browser or network latency, or requests that Azure rejects before they reach the container. A window with no eligible requests reports **No data**. We verify the workbook after the first live playtest.
