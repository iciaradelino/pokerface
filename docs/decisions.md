# Decision records

Each record states the context, the decision, the alternatives we rejected and the consequences.

## Storage and data model of the players service

**Status:** accepted, 11 November 2026. **Owner:** Laura. Tables and columns are in [data-model.md](data-model.md).

### Context

The players service stores profiles and chip balances, records the result of each hand sent by the game service, and serves the leaderboard. The game service retries when a call times out, so saving a result must be safe to repeat, and results can arrive late or in a different order than the hands were played. The course requires one database per service, SQL Server locally and a serverless Azure SQL database in the cloud. We only use the plain `mssql` driver and our own migration runner, with no ORM.

### Decision

- **Two tables in the `players` database:** `players` (name, avatar, chips, gesture settings) and `hand_results` (one row per player per finished hand). Only the players service reads them. The game service uses HTTP.
- **Identity:** a UUID generated by the database. There are no passwords. The browser keeps the id in `localStorage`, as in the plan.
- **Chips are derived from the results.** The balance is the starting stack (1000) plus the sum of every saved `delta`, limited to 0 up to the maximum `INT`. `players.chips` stores this value so that reading it and the leaderboard are cheap, and it is recomputed from `hand_results` inside the same transaction that inserts a result.
- **Safe retries:** the primary key of `hand_results` is (`hand_id`, `player_id`). A result whose key already exists changes nothing and still answers 200. The player's row is locked during the save, so two retries arriving together run one after the other.
- **Index on `hand_results(player_id)` including `delta`** (migration `003`), so the sum only reads the rows of one player.
- **Leaderboard:** a query on `players.chips` (top 10, ties broken by name), with no table of its own. It lives in the players service so it keeps working when the game service is down.
- **Small choices:** the avatar is a hex colour, gesture settings are JSON text checked with `ISJSON`, and `chips >= 0` is enforced by a `CHECK` constraint.
- **Raw SQL** with parameters, in one repository module, so the routes can be tested with an in-memory fake.

### Alternatives considered

- **Adjust the balance with each result** (`chips = max(0, chips + delta)`). This was our first version. It depends on arrival order: if a loss of 1500 arrives before an earlier win of 1000, the balance is clamped to 0 and the win then gives 1000 instead of 500. A reviewer found it and we replaced it.
- **No `chips` column, computed on every read.** Always correct, but the leaderboard would sum every result of every player on each request.
- **Allow negative balances.** Simpler arithmetic, but a player with negative chips makes no sense at a poker table.
- **A shared database with the game service.** Breaks the one-database-per-service rule and couples the services.
- **An ORM.** More packages and more to learn for four small queries. We also keep the migrations as plain numbered SQL files.
- **Storing avatars as images.** Needs file storage, which is out of scope. A colour plus the player's initials is enough for the UI.

### Consequences

- Retries and late results are safe, and the leaderboard works when the game service is down.
- The same starting stack of 1000 appears in the migration default and in the repository code (`STARTING_CHIPS`). They must be changed together.
- Each save sums all results of that player. The index makes this a seek, which is fine at our scale. If a player had very many hands we could keep a running total instead.
- Deleting a player deletes their results (`ON DELETE CASCADE`), so their history is lost.
- There is no real authentication: anyone who knows a player's id can edit or delete that profile. This is accepted for games between friends, as in the plan.
- Without the index in `003`, six players saving results at the same time made 145 of 150 saves fail with a 503 because of SQL Server deadlocks. With it all 150 succeed. We checked this with a manual load script. The unit tests use an in-memory repository, so they do not run the SQL and do not catch locking problems.
